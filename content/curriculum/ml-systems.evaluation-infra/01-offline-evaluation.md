Offline evaluation is how you decide whether to ship. It is also systematically
optimistic, for reasons that are structural rather than accidental, and knowing
where the optimism comes from is what keeps the number useful.

## The evaluation set is a product

```text
  it should be:
    □  REPRESENTATIVE of production traffic
    □  large enough for the effect sizes you care about
    □  STABLE, so results are comparable over time
    □  refreshed periodically, so it does not go stale
    □  SLICED, so aggregate performance cannot hide a
       collapsed segment
    □  version-controlled, like any other artifact
```

The tension between "stable" and "refreshed" is real and is resolved by keeping
both:

```text
  A FIXED BENCHMARK    never changes; comparable across years
                       → detects regressions
                       → goes stale relative to the world

  A ROLLING WINDOW     the most recent N days
                       → reflects current reality
                       → not comparable across time
```

Report both. A model that improves on the rolling set and regresses on the fixed
one has probably overfitted to recent conditions.

## Slices are not optional

```text
  overall accuracy    0.94

  by segment
    new users         0.71   ← the model is worst where it
    returning         0.96      matters most for growth
    mobile            0.89
    desktop           0.96
    English           0.95
    other languages   0.68
```

**A single aggregate number is nearly always hiding something like this.** The
slices worth defining in advance:

```text
  □  user segments that matter commercially
  □  geography and language
  □  device and platform
  □  new versus established entities (the cold-start slice)
  □  rare but high-cost classes
  □  time — recent versus older data
  □  any protected attribute where fairness is a requirement
```

The gate should be per-slice, not only aggregate: a model that improves overall
while regressing a slice beyond a threshold should not ship without a decision.

## Choosing the metric

```text
  match the metric to the DECISION, not to convention

  a ranked list shown to a user      →  NDCG, MRR, recall@k
  a threshold decision               →  precision/recall at the
                                        operating point
  a probability feeding a downstream
    calculation                      →  calibration, log loss
  a regression                       →  MAE if outliers should
                                        not dominate; RMSE if
                                        they should
  imbalanced classification          →  PR-AUC, not ROC-AUC
```

The last is worth expanding, because ROC-AUC is the default and is misleading on
imbalanced problems:

```text
  1% positive rate

  ROC-AUC 0.95 sounds excellent, and at a usable threshold
  precision may be 8%: 92 false alarms per true positive.

  → PR-AUC and precision@k reflect what the user experiences;
    ROC-AUC does not, because the false-positive rate is
    computed against an enormous negative class.
```

**Always report the metric at the operating point you will actually use**, not
only the threshold-free summary. A model is deployed at a threshold, and that is
where its behaviour matters.

## Baselines

```text
  ALWAYS compare against:
    □  the current production model
    □  a trivial baseline (majority class, most popular item,
       the previous value)
    □  a simple model (logistic regression, gradient boosting
       on a few features)
    □  a human, where one currently does the task
```

The trivial baseline is the one that catches embarrassment. A recommender that
does not beat "most popular" is not a recommender, and this is discovered
depressingly often *after* deployment.

## Why offline is optimistic

Five structural reasons, and each has a mitigation:

```text
  1. THE TEST SET IS FROM THE PAST
       production is always later. drift is guaranteed.
       → evaluate on the most recent closed window

  2. FEEDBACK LOOPS
       the data was generated by the CURRENT system, so it
       cannot show you what a different system would have done
       → exploration data, or off-policy evaluation

  3. SELECTION BIAS
       you only have labels for what was shown/approved/served
       → the censored-label problem from the framing chapter

  4. MULTIPLE COMPARISONS
       picking the best of forty configurations makes the
       validation metric optimistic
       → a test set touched once

  5. SKEW
       the offline features are not the serving features
       → the training/serving skew chapter
```

**Reason 2 is the deepest.** A recommender's logs contain engagement only with
items it chose to show. A new model that would have shown different items cannot
be evaluated on that data without correction, because the counterfactual is not
observed. This is why offline improvements so often fail to appear online, and it
is a genuine limitation rather than a measurement error.

## Counterfactual evaluation

The partial answer to reason 2:

```text
  INVERSE PROPENSITY SCORING

    if the logging policy showed item i with probability p,
    weight its observed outcome by 1/p when evaluating a new
    policy.

    → an unbiased estimate of the new policy's performance,
      PROVIDED
        □  the logging probabilities were RECORDED
        □  every item had non-zero probability of being shown
        □  the variance is manageable (small p → huge weights)
```

The precondition is what makes this an *infrastructure* concern rather than a
modelling one: **you must log the propensity at serving time.** A system that
records only what was shown, without the probability it was shown with, cannot do
this afterwards — the information is gone.

Adding a small amount of randomisation to serving, and logging the probabilities,
is a modest cost that makes offline evaluation of new policies possible. It is the
same exploration argument as the framing chapter, arriving from a different
direction.

## Testing beyond metrics

```text
  BEHAVIOURAL TESTS (CheckList-style)
    unit tests for models: specific inputs with expected
    behaviour

    INVARIANCE     a paraphrase should not change the label
    DIRECTIONAL    adding a strongly negative phrase should
                   not increase a positive score
    MINIMUM
    FUNCTIONALITY  the simplest possible cases must work
```

```text
  □  a curated set of KNOWN-HARD cases
  □  regression cases from past incidents  ← the highest value
  □  adversarial and malformed inputs
  □  boundary cases at the decision threshold
```

**The incident-regression set is the one to build first.** Every production
failure becomes a test case, and the suite grows into an institutional memory of
what has broken before — which is exactly what prevents the same class recurring.

## What to take away

1. The evaluation set is a versioned artifact; keep both a fixed benchmark for
   comparability and a rolling window for currency.
2. Slice-level gates are not optional — a single aggregate number is nearly always
   hiding a collapsed segment.
3. Match the metric to the decision, use PR-AUC rather than ROC-AUC on imbalanced
   problems, and always report performance at the actual operating point.
4. Compare against a trivial baseline; models that do not beat "most popular" are
   discovered after deployment more often than anyone admits.
5. Offline evaluation is structurally optimistic — the deepest reason is that logs
   only contain outcomes for what the current system chose to show.
6. Log serving propensities so counterfactual evaluation is possible later; without
   them the information is gone.

Next: online testing, which is the only measurement that actually settles it.
